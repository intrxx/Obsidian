I read through the project's C++ and found the biggest problems are in multiplayer save/load, the server-side item RPCs, and the damage formula. Everything below comes from reading the code; nothing was compiled or run, and .uasset content (Blueprints, behaviour trees, Mass configs) was not inspected.

What the project is: a Path-of-Exile-style ARPG on Unreal with a Lyra-like architecture, about 24k lines of game code in Source/Obsidian. The main systems are GAS (attributes, damage execution), a replicated item stack on the PlayerController (inventory, equipment, stash, crafting, item manager), item drops and labels, local save games, behaviour-tree AI, and a CommonUI front end. Mass exists only as a MassAgentComponent on the character base. Paths below are relative to Source/Obsidian.

1. Save system and multiplayer (most serious)

- Every hero loads the host's save. Private/Characters/Heroes/ObsidianHero.cpp:409 loads CurrentHeroSaveGame from the local GameInstance for any hero whose ability system initialises. On a listen server, joining players receive a copy of the host's inventory, equipment and personal stash. Their own save is never applied, because the load functions require authority.
- Shared stash has the same problem. Private/Characters/Player/ObsidianPlayerController.cpp:91 loads the server's shared stash into every PlayerController.
- Everyone spawns as the host's class. Private/Game/ObsidianGameMode.cpp:22 sets DefaultPawnClass from the host's save.
- Saving can overwrite your hero with someone else's. RequestSaveGame calls SaveData on every registered hero into the same save object, so the last one wins. Simulated proxies also register (via OnRep_PlayerState), and they have no controller, so they write an empty inventory.
- Save ID collision after deleting a hero. Private/Game/Save/ObsidianMasterSaveGame.cpp:152 uses Num() as the new ID. With heroes 0, 1, 2, deleting 1 makes the next hero ID 2, which reuses slot offline_hero_2 and overwrites the existing hero.
- A successful sync save reports failure. In Private/Game/Save/ObsidianSaveGameSubsystem.cpp:152-162 only the async branch returns; the sync branch falls through to the error log and broadcasts OnSavingFinished(nullptr, false).
- Smaller save issues:
  - DeleteHeroSave hardcodes user index 0 (:343).
  - ParallelFor touches UObjects off the game thread (:223, :253).
  - RegisterSaveable/UnregisterSaveable use hard checks, so a hero that ends play before its ability system initialised will crash.
  - LoadData teleports to the saved location with no map check (ObsidianHero.cpp:301), which is the origin for a new hero.
  - There is no autosave; saving only happens from the gameplay menu.

2. Item manager: server RPCs trust the client

All in Private/InventoryItems/ObsidianItemManagerComponent.cpp unless noted.

- Stack duplication. TakeOutFromItemInstance (Private/InventoryItems/Inventory/ObsidianInventoryComponent.cpp:579-591) clamps the amount for the cursor but removes the unclamped client value. Sending 0 or a negative number removes nothing and still puts one stack on the cursor. Sending more than the stack empties the entry and hands out count - 1.
- Equipped item duplication. ServerGrabEquippedItemToCursor (:572-574) ignores the result of UnequipItem. If equipment actions are blocked, the item stays equipped and also goes on the cursor.
- Dragged item can be silently destroyed. The grab and take-out RPCs (:212, :297, :346, :765) overwrite DraggedItem without checking it is empty.
- Dropping with nothing dragged. ServerHandleDroppingItem (:1157) never checks for an empty DraggedItem, and ignores a failed nav query (:1209), so the item spawns at the world origin.
- Stash works from anywhere. No stash RPC verifies the player is near a stash; opening it is purely client-side UI.
- Item spawner has no validation. ServerSpawnItemFromSpawner (ObsidianPlayerController.cpp:44) checks neither range nor CanInteract.
- Replicating a UClass as a subobject. :215-218, :897-900 and :914-918 pass ItemDef (a TSubclassOf) to AddReplicatedSubObject/ReplicateSubobject. The dragged Instance is also never registered after grabbing, which will break if you switch to the registered subobject list.

3. Inventory, stash and equipment logic

- Stack limits are not enforced consistently.
  - TryAddingStacksToExistingItems (ObsidianInventoryComponent.cpp:617-651) computes the inventory total once before the loop, so the limit can be exceeded across several stacks.
  - The stash counters are stubs returning 0 (Private/InventoryItems/PlayerStash/ObsidianPlayerStashComponent.cpp:174-184).
  - The checkf(CombinedStacks <= LimitStackCount) at :860/:883 then becomes a crash rather than a guard.
- Client crash risk in fast-array callbacks. PostReplicatedAdd/PreReplicatedRemove in the inventory and equipment lists dereference Entry.Instance (for example Private/InventoryItems/Inventory/ObsidianInventoryGridItemList.cpp:278-295). That pointer can still be null on a client when the subobject arrives late.
- Banned-category functions do nothing. Private/InventoryItems/Equipment/ObsidianEquipmentComponent.cpp:976-1010 modify a by-value copy returned by FindEquipmentSlotByTag.
- Null dereference. GetItemLocationFromGrid (ObsidianInventoryComponent.cpp:1065) dereferences FindKey without checking it.
- Requirements are only checked at equip time. Removing the item that grants the required stat leaves dependent items equipped, and WeaponSwap does not check the block tag.
- Heavy duplication. Inventory, stash and equipment each carry near-identical add/replace/stack code in instance and definition variants. The limit bug above is one result.
- Debug leftovers. There are many GEngine->AddOnScreenDebugMessage calls and LogTemp warnings on gameplay paths.

4. Ability system and damage

- Armour barely does anything. Private/AbilitySystem/Executions/ObsidianDamageExecution.cpp:242 subtracts the mitigation fraction (0 to 1) as flat damage instead of multiplying by 1 - mitigation.
- Chaos damage uses cold resistance. :345 is a copy-paste of the cold block.
- Shock is never applied. The effect is built and the apply call is commented out (:448).
- Crash on kills without a character source. Private/AbilitySystem/Attributes/ObsidianCommonAttributeSet.cpp:174 dereferences SourceCharacter, which is null for damage volumes or a damage-over-time effect whose source is gone.
- Death only triggers through IncomingDamage. Effects that lower Health directly (the debug HP volumes do) can leave a unit alive at 0 HP.
- Division by zero in the effect UI. Private/AbilitySystem/ObsidianAbilitySystemComponent.cpp:131 divides duration by period, which is 0 for non-periodic duration effects.
- Minimum of 1 on resources with a max of 0. Private/AbilitySystem/Attributes/ObsidianHeroAttributeSet.cpp:64-69 clamps energy shield, mana and stamina to at least 1.
- Deprecation warnings stay off. ObsidianAbilitySystemComponent.cpp:61,75 use PRAGMA_DISABLE_... where ENABLE was intended.
- Unfinished rules. Roughly ten if(true) //TODO branches are unimplemented (hit vs spell, combat area), and XP is a flat 200 per kill.

5. Characters, interaction and drops

- Hero is destroyed the moment death starts. ObsidianHero.cpp:57 binds OnDeathFinished to the OnDeathStarted delegate. The hero is torn down about 0.1s later, cutting off the death montage.
- Null dereference in interaction. Private/CharacterComponents/ObsidianPlayerInputManager.cpp:750 checks InteractionTarget but dereferences ActiveInteractionTarget, which an abandon or stop can clear first.
- Item spawner drop limit is broken. Private/InventoryItems/Items/ObsidianItemSpawner.cpp:37 re-adds the finished delegate on every interaction, after the broadcast has already fired. TimesDropped goes 0, 1, 3, 6, so == TimesToDrop can be skipped and the spawner never turns off.
- Possible out-of-range index in drops. Private/InventoryItems/ItemDrop/ObsidianItemDropComponent.cpp:168 indexes TreasureClasses even when only must-roll classes exist.
- Drops at the origin on nav failure. :819 uses the unset location; this one is already marked TODO.
- Death montage index is biased. A float RandRange used as an index almost never picks the last montage (hero and enemy).

6. AI and projectiles

- Target search scales poorly. Private/AI/Services/ObsidianBTService_FindNearestPlayer.cpp:37 runs GetAllActorsWithTag every 0.5s per enemy and does not skip dead players. This will hurt as enemy counts grow.
- Boss loses its target in multiplayer. Private/AI/ObsidianBossAIController.cpp:66 clears the target when any one hero drops out of perception, even if another is visible. It also uses Blackboard unchecked and re-binds the perception delegate on every possess.
- Projectile null dereference. Private/Combat/Projectile/ObsidianProjectileBase.cpp:72 dereferences the damage spec without a validity check.
- Uncommitted team-ID change does not replicate. TeamId on the hero and controller is not replicated and the setter notifies nothing. It is fine for server-side perception only.

Not reviewed in depth

- UI widget controllers, including the 2,000-line ObInventoryItemsWidgetController.cpp.
- Crafting and affix generation.
- Stash tab classes.
- The item label solver beyond its tick; it logs at Warning every solve.
- The third-party plugins (CommonGame, CommonUser, AsyncMixin, GameplayMessageRouter).

If you want to start fixing, I would begin with section 1 (decide who owns save data in co-op) and the two duplication bugs in section 2.
